# ML-подходы в системе распознавания лиц

---

## 1. Обзор CV/ML-задач

Система распознавания лиц на проходной решает несколько последовательных CV/ML-задач, каждая из которых критична для конечного качества и скорости работы. Ниже приведено описание каждой задачи, выбранный подход и обоснование.

| Этап | Задача | Выбранный подход | Ключевое требование |
|------|--------|------------------|---------------------|
| 1 | Детекция лица | YOLO-Face | Скорость < 50 мс, точность > 95% |
| 2 | Оценка качества кадра | SER-FIQ | Отбраковка непригодных кадров |
| 3 | Liveness / anti-spoofing | Texture + Motion + Depth | FAR < 0.01% от spoofing-атак |
| 4 | Извлечение эмбеддинга | ArcFace (512 dim) | TAR > 99% при FAR = 0.01% |
| 5 | Поиск в базе | FAISS (IVF + PQ) | sub-second на 12 000+ векторов |
| 6 | Принятие решения | Правила + пороги | Баланс FAR/FRR |

---

## 2. Детекция лица

### 2.1. Выбор модели: YOLO-Face

**Почему YOLO-Face:**
- Специализированная версия YOLO для детекции лиц (обучена на WIDER Face)
- Время инференса: < 50 мс на кадр (на NVIDIA Jetson)
- Точность: mAP > 90% на WIDER Face (hard subset)
- Поддерживает детекцию нескольких лиц на кадре (до 5)
- Работает в реальном времени (30 fps)

**Альтернативы, которые рассматривались:**
- MTCNN: точнее, но медленнее (~150 мс) — не подходит по latency
- Haar Cascade: быстрый, но низкая точность в сложных условиях (очки, повороты) — не подходит по качеству
- RetinaFace: хороший баланс, но сложнее в развертывании на edge

### 2.2. Постобработка

- Отбрасывание лиц с уверенностью < 0.5
- Отбрасывание лиц с размером < 60px (слишком мелкие для распознавания)
- Выбор лица с максимальной уверенностью (если несколько)
- Выравнивание лица по глазам (alignment) перед передачей в эмбеддинг-модель

### 2.3. Baseline для сравнения

- MTCNN (точность 95%, latency 150 мс)
- Если YOLO-Face не покажет ожидаемого качества на реальных данных, планируется замена на RetinaFace

---

## 3. Оценка качества кадра

### 3.1. Выбор модели: SER-FIQ

**Почему SER-FIQ:**
- Специализированная модель для оценки качества изображений лиц
- Оценивает: размер лица, резкость, освещенность, угол поворота, заслонение
- Выход: score от 0 до 1
- Время: < 30 мс

**Критерии качества:**
- Размер лица: > 60px (иначе слишком мало для распознавания)
- Резкость: вариация Лапласа > 100 (иначе размыто)
- Освещенность: средняя яркость > 30 и < 220 (иначе пересвет или темнота)
- Угол поворота: roll, pitch, yaw < 30 градусов (иначе лицо не в фас)
- Заслонение: отсутствие масок, очков (влияет на качество)

### 3.2. Порог качества

- quality_score >= 0.7 — кадр пригоден для распознавания
- quality_score < 0.7 — immediate manual_review (без попытки распознавания)

### 3.3. Альтернативы

- FaceQNet — альтернативная модель оценки качества
- Если SER-FIQ не покажет ожидаемой корреляции с качеством распознавания, планируется замена на FaceQNet или обучение собственной модели на реальных данных

## 4. Liveness и anti-spoofing

### 4.1. Комбинированный подход

Защита от spoofing реализована как комбинация трех методов, работающих параллельно:

**4.1.1. Texture analysis (обнаружение фото/печати)**
- Метод: LBP (Local Binary Patterns) + BRISK (Binary Robust Invariant Scalable Keypoints)
- Анализирует текстуру кожи, ищет артефакты печати, блики, пиксельную сетку
- Выход: texture_score от 0 до 1
- Время: < 50 мс

**4.1.2. Motion detection (обнаружение микро-движений)**
- Метод: optical flow (Farneback)
- Анализирует микро-движения: моргание, поворот головы, микровыражения
- Выход: motion_score от 0 до 1
- Время: < 40 мс

**4.1.3. Depth estimation (обнаружение плоских объектов)**
- Метод: MediaPipe Face Mesh
- Оценивает 3D-структуру лица, ищет признаки плоского объекта (фото на экране, распечатка)
- Выход: depth_score от 0 до 1
- Время: < 30 мс

### 4.2. Итоговый liveness_score

```
liveness_score = (texture_score + motion_score + depth_score) / 3
```

- liveness_score >= 0.8 — liveness подтвержден
- liveness_score < 0.8 — manual_review (возможна атака)

### 4.3. Альтернативы

- Если комбинированный подход не даст FAR < 0.01%, планируется замена на специализированную модель anti-spoofing (например, DeepFakeDetection или специально обученную на реальных атаках)
- Использование ИК-камеры для оценки глубины (альтернатива MediaPipe)

## 5. Извлечение эмбеддинга

### 5.1. Выбор модели: ArcFace

**Почему ArcFace:**
- State-of-the-art на задачах распознавания лиц
- TAR (True Acceptance Rate) > 99% при FAR = 0.01% на LFW и IJB-C
- Размерность эмбеддинга: 512 (компактно, быстрое сравнение)
- Время инференса: < 100 мс
- Хорошо работает с выровненными лицами (alignment)

**Альтернативы:**
- FaceNet (Google) — хорошее качество, но больше размерность (1024)
- AdaFace — новее, может дать лучший TAR на сложных датасетах
- Если ArcFace не покажет ожидаемого качества на реальных данных, планируется замена на AdaFace или обучение собственной модели на специфических данных кампуса

### 5.2. Предобработка перед эмбеддингом

- Выравнивание лица по глазам (alignment) с использованием 5 ключевых точек (глаза, нос, рот)
- Нормализация размера: 112×112 пикселей
- Нормализация цветов: приведение к стандартному распределению

### 5.3. Постобработка эмбеддинга

- L2-нормализация вектора (для корректного косинусного сходства)
- Результат: вектор размерностью 512 (float32), нормализованный

## 6. Поиск в базе (one-to-many)

### 6.1. Verification vs Identification

| Характеристика | Verification (1:1) | Identification (1:N) |
|----------------|--------------------|----------------------|
| Сравнение | Одно лицо с одним в базе | Одно лицо со всей базой |
| Сложность | O(1) | O(N) |
| Применение | Разблокировка телефона | Проходная (найти среди 12 000) |
| На проходной | **Не используется** | **Используется** |

На проходной нужна **identification**: найти лицо сотрудника среди 12 000 в базе. Это требует эффективного поиска (ANN), так как полный перебор O(12 000) дает latency ~ 600-800 мс, что вписывается в 1 секунду, но при росте до 100 000+ уже не подходит.

### 6.2. Выбор подхода: FAISS (IVF + PQ)

**Почему FAISS:**
- Специализированная библиотека для эффективного поиска по эмбеддингам
- Поддерживает индексы IVF (Inverted File) + PQ (Product Quantization)
- На 12 000 векторов: поиск < 200 мс
- На 100 000 векторов: поиск < 500 мс (при оптимизации)
- Масштабируется горизонтально (шардирование)

**Конфигурация индекса:**
- nlist = 256 (количество центроидов IVF)
- m = 8 (количество подвекторов PQ)
- nbits = 8 (количество бит на подвектор)
- Используется косинусное сходство (нормализованные векторы)

**Альтернативы:**
- Annoy (Spotify) — проще, но медленнее на больших базах
- ScaNN (Google) — быстрее, но сложнее в настройке
- Если FAISS не даст sub-second на 12 000, планируется переход на ScaNN

### 6.3. Edge-кеш

- Топ-1000 сотрудников по частоте проходов кешируются на edge
- Поиск в кеше: < 50 мс
- При потере сети система работает на кеше (с повышенным порогом 0.8)

## 7. Пороги и принятие решений

### 7.1. Пороги

| Порог | Значение | Обоснование |
|-------|----------|-------------|
| match_score для allow | >= 0.75 | FAR < 0.01% на тестовых данных |
| match_score для manual_review | 0.55 - 0.75 | Зона неопределенности |
| match_score для deny | < 0.55 | Четко не совпадает |
| margin_to_second_best | >= 0.1 | Защита от двух близких кандидатов |
| quality_score | >= 0.7 | Обеспечивает качество распознавания |
| liveness_score | >= 0.8 | Защита от spoofing |

### 7.2. Как выбирались пороги

Пороги выбирались на основе анализа FAR/FRR на валидационном наборе:

1. **match_score:** На тестовых данных (LFW, IJB-C) при match_score = 0.75 FAR ≈ 0.01%, FRR ≈ 1%. Это оптимальный баланс, так как цена false accept (безопасность) выше цены false reject (очередь).

2. **margin_to_second_best:** При марже < 0.1 система часто ошибается между двумя похожими людьми (близнецы, плохое качество). Порог 0.1 исключает большинство таких случаев.

3. **quality_score:** Порог 0.7 выбран эмпирически — при этом качестве ARC Face дает стабильные результаты. Ниже 0.7 — качество слишком низкое, распознавание ненадежно.

4. **liveness_score:** Порог 0.8 выбран для защиты от spoofing (фото/видео). При пороге 0.8 FAR от spoofing-атак < 0.01%.

### 7.3. Баланс FAR/FRR

| Решение | FAR (False Accept) | FRR (False Reject) |
|---------|--------------------|--------------------|
| allow | < 0.01% | < 1% |
| manual_review | - | - |
| deny | 0% | < 5% (переход на manual_review) |

**Цена ошибок:**
- False Accept: инцидент безопасности, возможен проход постороннего
- False Reject: очередь в пик, недовольство сотрудников, нагрузка на охрану

**Приоритет:** FAR < FRR, так как цена false accept значительно выше.

## 8. Правила vs Модель

| Решение | Правила | Модель |
|---------|---------|--------|
| Детекция лица | - | YOLO-Face |
| Оценка качества | Пороги (size, sharpness, brightness) | SER-FIQ (quality_score) |
| Liveness | - | Комбинация моделей (texture, motion, depth) |
| Извлечение эмбеддинга | - | ArcFace |
| Поиск в базе | - | FAISS (ANN) |
| Принятие решения | match_score >= 0.75, margin >= 0.1, quality >= 0.7, liveness >= 0.8 | - |
| Offline-режим | Повышенный порог (0.8) | - |

**Правила:** используются для принятия финального решения (allow / manual_review / deny) на основе выходов моделей. Правила прозрачны, объяснимы и легко настраиваются.

**Модели:** используются для извлечения признаков (эмбеддингов), оценки качества и liveness. Модели сложны для интерпретации, но обеспечивают высокую точность.

| Компонент | Готовая модель | Собственное обучение |
|-----------|----------------|---------------------|
| Детекция лица | YOLO-Face (предобученный на WIDER Face) | Не требуется (достаточно качества) |
| Оценка качества | SER-FIQ (предобученный) | Не требуется |
| Liveness | Комбинация методов (LBP, optical flow, MediaPipe) | Не требуется |
| Извлечение эмбеддинга | ArcFace (предобученный на MS1M) | Возможно дообучение на данных кампуса |
| Поиск в базе | FAISS (библиотека) | Не требуется |

**Обоснование:** готовые модели обеспечивают достаточное качество для MVP и первых пилотов. Собственное обучение требует большого размеченного датасета (тысячи лиц, разные условия, несколько камер), что дорого и долго. Если на пилоте качество окажется ниже требуемого, можно дообучить ArcFace на реальных данных с проходных (с соблюдением всех требований privacy).

## 10. Baseline и технические метрики

### 10.1. Baseline

| Baseline | Описание | Ожидаемый результат |
|----------|----------|---------------------|
| 1 | Полный перебор (O(N)) по базе 12 000 | latency ~ 600-800 мс |
| 2 | FAISS с IVF (без PQ) | latency ~ 300 мс |
| 3 | FAISS с IVF + PQ (целевой) | latency ~ 150-200 мс |

**Целевой baseline:** FAISS IVF + PQ обеспечивает sub-second поиск (200 мс) на 12 000 векторов, что вписывается в общий бюджет latency (1000 мс).

### 10.2. Технические метрики для выбора

| Метрика | Целевое значение | Как измеряется |
|---------|------------------|----------------|
| FAR (False Accept Rate) | < 0.01% | На тестовых данных (LFW, IJB-C) |
| FRR (False Reject Rate) | < 1% | На тестовых данных (LFW, IJB-C) |
| TAR (True Accept Rate) | > 99% | При FAR = 0.01% (LFW) |
| EER (Equal Error Rate) | ~0.5% | На тестовых данных |
| Latency (p95) | < 1000 мс | Измеряется на проходной (end-to-end) |
| Throughput | > 20 проходов/мин | Измеряется в пик (утром) |

## 11. Validation и предотвращение утечек

### 11.1. Сплит по личностям

**Критическое требование:** валидационный набор должен быть разделен по личностям, а не по кадрам. Это предотвращает утечку данных, когда лицо одного человека попадает и в train, и в test.

**Правильный подход:**
- Train: 70% сотрудников
- Val: 15% сотрудников
- Test: 15% сотрудников

**Неправильный подход:**
- Train: 70% кадров каждого сотрудника
- Val: 15% кадров каждого сотрудника
- Test: 15% кадров каждого сотрудника
→ Утечка, так как модель видела лицо этого сотрудника на train и запомнила его.

### 11.2. Разные условия съемки

Валидационный набор должен включать кадры, снятые в разных условиях:
- Разные камеры (разные проходные)
- Разное освещение (утро, день, вечер, искусственное)
- Разные ракурсы (анфас, поворот 15°, 30°)
- Разные дни (неделя, выходные, праздники)

### 11.3. Проверка по подгруппам

Качество модели должно проверяться отдельно по подгруппам:
- По возрасту (молодые/взрослые)
- По полу
- По этнической принадлежности (если данные позволяют)
- По условиям съемки (хорошее/плохое освещение)

Если модель показывает худшее качество на какой-либо подгруппе, это повод для дообучения или корректировки.

### 11.4. Обработка delayed labels

Delayed labels — это информация о правильности решения, которая становится известна только после события:

1. **Ручные проверки охраны:** если охрана изменила решение системы (deny → allow или allow → deny), это должно быть зафиксировано и использовано для дообучения.

2. **Жалобы сотрудников:** если сотрудник жалуется, что его не пустили (false reject), это feedback для улучшения модели.

3. **Проход по карте после отказа:** если система сказала deny, а сотрудник прошел по карте — это признак false reject (если он действительно был в базе).

**Процесс:**
1. Сбор delayed labels в отдельную таблицу (event_id, decision, actual_decision, reason)
2. Еженедельный анализ расхождений
3. При накоплении 100+ расхождений — пересмотр порогов или дообучение модели

## 12. LLM в системе

### 12.1. Нужен ли LLM?

**Нет,** LLM не используется в контуре принятия решения allow/deny. Причины:

1. **Скорость:** LLM требует значительных вычислительных ресурсов (несколько секунд на инференс), что нарушает требование < 1 секунды.

2. **Детерминированность:** LLM дает вероятностный ответ, который не подходит для критической задачи контроля доступа (решение должно быть детерминированным и объяснимым).

3. **Безопасность:** LLM может быть подвержен атакам (prompt injection), что создает риск для системы безопасности.

4. **Стоимость:** LLM дороже в эксплуатации (высокие вычислительные затраты) по сравнению с ML-моделями.

### 12.2. Где LLM может быть полезен

**Вне контура allow/deny:**

1. **Генерация отчетов:** автоматическое описание инцидентов для охраны и безопасности (например, "Сотрудник X не прошел по лицу из-за низкого качества кадра, причина: плохое освещение").

2. **Ответы на вопросы сотрудников:** чат-бот для сотрудников с вопросами о работе системы ("Почему меня не пустили?", "Как зарегистрировать лицо?").

3. **Анализ жалоб:** классификация и агрегация жалоб сотрудников на систему для выявления системных проблем.

4. **Продуктовая аналитика:** генерация еженедельных отчетов по метрикам для руководства.

**Решение:** LLM используется только как вспомогательный инструмент для повышения удобства и аналитики, но НЕ влияет на решение о доступе.
