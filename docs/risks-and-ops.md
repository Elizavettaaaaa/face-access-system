# Риски и эксплуатация системы распознавания лиц

---

## 1. Надежность и деградация

### 1.1. Edge-кеш и работа при потере сети

- **Edge-устройство** хранит локальный кеш эмбеддингов топ-1000 сотрудников по частоте проходов.
- Кеш обновляется ежечасно из центрального сервиса.
- При потере сети система переходит в **offline-режим**:
    - Поиск выполняется только по локальному кешу.
    - Порог allow повышается с 0.75 до 0.8 (снижение FAR).
    - События логируются локально в буфер.
    - После восстановления сети буфер синхронизируется с центральным Audit Log.
- **Время работы в offline-режиме:** до 24 часов (кеш актуален, сотрудники не увольняются массово).
- **Ограничение:** новые сотрудники не попадают в кеш до синхронизации, поэтому они могут не пройти по лицу (используют карту-пропуск).

### 1.2. Идемпотентность команд турникету

- Каждая команда турникету (`open`, `close`) имеет уникальный ID (UUID).
- Турникет хранит историю последних 100 команд.
- При повторной отправке команды с тем же ID турникет не выполняет действие повторно (защита от двойного открытия).
- Если турникет не подтвердил выполнение команды в течение 2 секунд, система повторяет команду (с тем же ID).
- При недоступности турникета система отправляет уведомление охране и переходит на fallback (карта-пропуск).

### 1.3. Fallback-стратегии

| Сбой | Fallback | Время переключения |
|------|----------|-------------------|
| Потеря сети на edge | Offline-режим (кеш) | Мгновенно |
| Недоступность центрального ANN | Edge-кеш (даже если не топ-1000) | < 1 минута |
| Недоступность базы данных | Кеш Redis (в центре) | < 1 минута |
| Недоступность турникета | Уведомление охране, ручное открытие | 2 минуты |
| Недоступность камеры | Вторая камера на проходной | Мгновенно |
| Сбой модели на edge | Переход на центральный сервис | < 1 минута |
| Общая недоступность системы | Полный fallback на карты-пропуска | < 5 минут |

### 1.4. Мониторинг надежности

- **Доступность edge-узлов:** проверка heartbeat каждые 10 секунд.
- **Доступность центрального сервиса:** проверка healthcheck каждые 5 секунд.
- **Качество сети:** мониторинг latency и packet loss между edge и центром.
- **Время реакции:** при потере связи edge переходит в offline-режим автоматически.
- **Алерты:** при недоступности любого компонента > 1 минуты.

## 2. Privacy, безопасность и управление данными

### 2.1. Какие данные считаются биометрическими

- **Эмбеддинги (512 dim):** считаются биометрическими данными (по 152-ФЗ).
- **Исходные изображения лиц:** не хранятся (кроме случаев расследования).
- **Метаданные:** не считаются биометрическими (ID сотрудника, время, место).
- **Кадры для расследования:** хранятся 90 дней, доступ только по запросу безопасности.

### 2.2. Хранение эмбеддингов

- **Формат:** только эмбеддинги (векторы 512 dim), исходные изображения не хранятся.
- **Шифрование:** AES-256-GCM на уровне базы данных.
- **Ключи:** хранятся в HashiCorp Vault, доступ только у сервисов.
- **Срок хранения:** до увольнения сотрудника + 30 дней (согласие на биометрию).
- **Удаление:** при увольнении — немедленный invalidate в центре, edge-синхронизация в течение 1 часа.

### 2.3. Доступ к данным

| Роль | Доступ | Условия |
|------|--------|---------|
| Система (service-to-service) | Чтение/запись эмбеддингов | JWT-токен, TLS 1.3 |
| Безопасность | Audit Log (чтение) | Двухфакторная аутентификация, по запросу |
| HR | Метаданные сотрудников | Двухфакторная аутентификация |
| Инженеры | Логи, метрики (без биометрии) | Доступ к мониторингу, не к базе |

### 2.4. Удаление сотрудника и отзыв согласия

1. **Увольнение:** HR отправляет событие в систему → немедленный invalidate в центре.
2. **Edge-синхронизация:** в течение 1 часа эмбеддинг удаляется из всех edge-кешей.
3. **Отзыв согласия:** сотрудник может отозвать согласие на биометрию → эмбеддинг удаляется в течение 24 часов.
4. **Полное удаление:** через 30 дней после увольнения все данные сотрудника удаляются (согласие истекло).

### 2.5. Защита от model inversion и утечки шаблонов

- **Model inversion:** невозможно восстановить лицо из эмбеддинга (512 dim → информационная потеря).
- **Утечка шаблонов:** эмбеддинги хранятся в зашифрованном виде, доступ только у сервисов.
- **Атака на API:** rate limiting (100 запросов/сек), аутентификация по JWT.
- **Атака на базу:** база доступна только через API (нет прямого доступа).

### 2.6. Аудит доступа к данным

- Все запросы к базе эмбеддингов логируются (кто, когда, зачем).
- Все запросы к Audit Log логируются (audit of audit).
- Логи защищены от изменения (append-only, SHA-256 подпись).
- Ежеквартальный аудит безопасности (внешний).

### 2.7. Почему некоторые решения нельзя принимать полностью автоматически

**Сомнительные случаи (low confidence):**
- match_score в зоне 0.55-0.75 → manual_review
- margin_to_second_best < 0.1 → manual_review
- quality_score < 0.7 → manual_review
- liveness_score < 0.8 → manual_review

**Увольнение и отзыв доступа:**
- Требует человеческого контроля (HR + безопасность), чтобы исключить ошибки.

**Изменение порогов и правил:**
- Требует review-процесса с участием безопасности и продуктовой команды.

### 2.8. Юридические требования

- **152-ФЗ:** хранение биометрии требует согласия, ограниченного срока хранения.
- **242-ФЗ:** локализация данных на территории РФ (если применимо).
- **266-ФЗ:** требования к биометрическим системам.
- **Требования:** юридический аудит перед запуском, согласие сотрудников, уведомление Роскомнадзора (при необходимости).

## 3. Операционные риски

### 3.1. Нагрузка в пик

- Утром 8:45-9:45 до 20 проходов в минуту на одну проходную.
- Edge-устройство должно выдерживать 20 запросов/мин (около 0.33 запроса/сек) — это не критично.
- Центральный сервис выдерживает пиковые нагрузки от 3 проходных → ~60 запросов/мин.

### 3.2. Деградация качества

- При ухудшении освещения (осень/зима) quality_score может снизиться.
- При массовом ношении масок (сезон гриппа) FRR может вырасти.
- **План:** ежемесячный мониторинг, дообучение моделей при необходимости.

### 3.3. Человеческий фактор

- Охрана может уставать и пропускать ошибки в ручной проверке.
- Сотрудники могут пытаться обойти систему (закрывать лицо, использовать фото).
- **План:** обучение охраны, регулярные проверки, audit-log для расследования.

### 3.4. Отказ оборудования

- Камера может выйти из строя → переключение на вторую камеру.
- Edge-узел может выйти из строя → переключение на другую проходную (или fallback на карты).
- **План:** резервное оборудование, SLA с поставщиками.

## 4. Риски безопасности

### 4.1. Spoofing-атаки

- **Фото на телефоне:** texture analysis (LBP) обнаруживает артефакты печати.
- **Распечатка:** texture analysis + depth estimation (MediaPipe) обнаруживает плоский объект.
- **Видео на экране:** motion detection (optical flow) обнаруживает отсутствие микро-движений.
- **3D-маска:** depth estimation обнаруживает отсутствие глубины (если не качественная).

### 4.2. Утечка данных

- **База эмбеддингов:** шифрование AES-256, доступ только у сервисов.
- **Audit Log:** append-only, SHA-256 подпись, доступ только уполномоченным.
- **Сеть:** TLS 1.3 для всех соединений.
- **Риск:** минимальный при соблюдении всех политик.

### 4.3. Внутренние угрозы

- Инженеры могут иметь доступ к логам (без биометрии).
- Безопасность и HR имеют доступ к Audit Log.
- **План:** разделение доступа, двухфакторная аутентификация, аудит доступа.

## 5. Экономические риски

### 5.1. Окупаемость

- CAPEX: 630 000 рублей.
- Годовая экономия: 400 000 рублей.
- Окупаемость: 1.6 года.
- **Риск:** если FRR > 5%, экономия снижается, окупаемость смещается до 2.5 лет.

### 5.2. Стоимость эксплуатации

- Edge-узлы: электроэнергия, обслуживание.
- Центральный сервис: облачные ресурсы.
- Охрана: обучение, поддержка.
- **Риск:** рост числа проходных увеличивает CAPEX и OPEX.

### 5.3. Штрафы и регуляторные риски

- Нарушение 152-ФЗ → штрафы до 1 млн рублей.
- Утечка биометрии → репутационные потери, иски.
- **План:** юридический аудит перед запуском, регулярные проверки безопасности.
